# Ouroboros GNOME Client

**Передача разработчику:** [HANDOFF.md](HANDOFF.md). Разработка на паузе; полное покрытие API не подтверждено.

[Карта покрытия API](docs/API-COVERAGE.md) сопоставляет контракт шлюза с нативными модулями и перечисляет выявленные пробелы и границы проверки.

Если результат записи настроек неизвестен, обычные правки остаются в форме. Повторная отправка блокируется до отдельного чтения кнопкой «Проверить результат записи»; совпадение текущих значений не выдаётся за исходную квитанцию. Отправленные секретные поля и чувствительные настройки подключений очищаются. Проверка: `npm run test:settings-write-recovery:gjs`.

Если ответ создания задания входа в аккаунт содержит ID, но не проходит проверку, клиент сохраняет ID и оставляет чтение/отмену доступными. Новый вход блокируется до разрешения этого задания; некорректный ответ не показывает ссылку, код или команду подключения. Отдельно прочитанное состояние отмечается отдельно от исходной квитанции. Проверка: `npm run test:account-login-receipt:gjs`.

В «Движок диктовки…» можно выбрать «PocketSphinx · English (US)» для нативного распознавания на устройстве. Flatpak включает движок и модель; запись ограничена 15 секундами, выбор действует в текущем окне до закрытия подключения и сохраняет прежнюю настройку движка на шлюзе. Текст вставляется в черновик; если во время распознавания он изменился или открыта другая комната, результат предлагается для отдельной вставки в исходной комнате. Проверки: `npm run test:local-dictation:gjs` и `npm run test:local-recognition:gjs`. Они используют настоящую запись речи и модель, без физического микрофона. Перед расшифровкой локальный WebRTC VAD отсекает записи без обнаруженной речи; он может ошибаться на шуме и очень коротких репликах. Другие языки и полное покрытие Web Speech API остаются открытыми.

Проверенные модули навыков также получают интерфейс `SpeechRecognition`/`webkitSpeechRecognition`, когда локальный движок доступен. Стандартный `browser_speech` проверен с его исходным JavaScript: нативное разрешение на микрофон → GStreamer → VAD/PocketSphinx → текст в GTK-черновике. Перед захватом показаны навык, шлюз и ограничение English (US); нативная кнопка останавливает захват и распознавание. Непрерывный режим сохраняет один поток захвата во время обработки блоков. Если движок не успевает, запись останавливается с сообщением. Проверка: `npm run test:host-recognition:gjs`. Это ещё не полная реализация Web Speech API: промежуточных результатов и входа MediaStreamTrack нет; границы блоков могут влиять на распознавание отдельных слов.

Изменение проекта подтверждается только записью того же ID/комнаты с отправленными значениями. Неизвестный ответ сохраняет черновик и блокирует повтор до отдельного чтения; совпадение текущего состояния показано отдельно от квитанции исходного запроса. Проверка: `npm run test:project-update:gjs`.

В «Сведениях о проекте» можно перечитать запись по ID: происхождение папки, опубликованную активность, решение о закрытии и ревизии. Последний полученный ответ создания/изменения показан отдельно и хранится только до закрытия подключения. Проверка: `npm run test:project-details:gjs`.

В резервном режиме окно задачи предлагает Pause и Hurry только для проверенной корневой попытки, включая согласованные маркеры повтора по таймауту. Старые кнопки и неподтверждённые повторы проверяют текущую принадлежность задачи. Проверка: `npm run test:task-lineage:gjs`.

Поздняя квитанция отправленного сообщения не заменяет статус нового черновика. Изменение текста или цитаты во время сохранения параметров комнаты требует повторного явного нажатия «Отправить». Проверка: `npm run test:room-cognition-chat:gjs`.

В задаче с режимом Swarm доступен нативный отчёт квитанции: покрытие, интервалы, ожидания, причинные связи, расходы и маршруты учёта. Неизвестные суммы и неполные причинные пути отмечаются отдельно; раскрытые разделы сохраняются при обновлении. Проверка: `npm run test:swarm-receipt:gjs`.

Модули навыков могут использовать настоящий WebKit `getDisplayMedia` для демонстрации экрана или окна. Нативный диалог называет навык и шлюз, индикатор позволяет остановить захват, а камера и экран разделяют общую блокировку. Выбор источника обслуживает системный путь WebKit/PipeWire; автоматические проверки используют mock display без захвата рабочего стола владельца. Проверка: `npm run test:host-media:gjs`.

Индикатор вызова в заголовке показывает исходную комнату и время с первого подключения, сохраняет отсчёт при переподключении и позволяет завершить звонок с любой страницы. Возврат открывает комнату самого вызова. Проверка: `npm run test:call-panel:gjs`.

Включение и локальное удаление навыка показывают проверенную квитанцию отдельно от текущего списка навыков. Неполный или чужой ответ не выдаётся за успех; удаление раскрывает подтверждённые путь, версию и признак удаления сохранённого состояния. Проверка: `npm run test:skill-mutations:gjs`.

Карточка вопроса различает активное ожидание, открытый вопрос без ожидания и вопрос, чья задача уже продолжилась. Завершение ожидания не закрывает разрешённый поздний ответ; обновление истории сохраняет выбранный вариант и черновик. Проверка: `npm run test:question-wait:gjs`.

Общий прогон: `python3 scripts/test-native-suite.py` при заданных `OUROBOROS_REFERENCE` и `OUROBOROS_TEST_PYTHON`. Он собирает клиент один раз, последовательно запускает все `test:*` команды из package.json и сохраняет JSON-отчёт, хеши входных файлов и отдельные журналы. Для поднабора повторите `--test имя-команды`; по умолчанию прогон останавливается на первом отказе, `--keep-going` сохраняет остальные результаты. Последний полный запуск 13 ноября 2026 выполнил все 199 команд: 198 прошли, `routing-journal` завершился с отказом запуска дисплея Xvfb и прошёл при отдельном повторе. Для всех 199 команд есть успешные результаты на неизменном снимке входных файлов; исходный отчёт сохраняет статус отказа, а сводная проверка и журналы указаны в карте покрытия. Этот запуск предшествует изменению legacy-гейтов задач. После добавления `test:task-lineage:gjs`, `test:project-details:gjs` и `test:project-update:gjs` текущий набор содержит 202 команды; полный набор из 202 пока не выполнялся. Эти результаты подтверждают перечисленные сценарии, а не полноту всего API.

Окно квот отдельно показывает ответ обновления: опубликованное время, сведения о пропуске проверки, снимки квоты, причины отсутствия данных и ресурсы. Текущее состояние читается отдельным GET; потерянный ответ не вызывает автоматический повтор обновления. Проверка: `npm run test:quota-refresh:gjs`.

В деталях навыка сохранены подробности ответа на отказ операции: допустимые ключи/разрешения, отклонённые элементы, причина, состояние проверки и зависимости. Они показаны отдельно от актуального списка навыков; новый запрос заменяет прежние детали. Проверка: `npm run test:skill-action-refusal:gjs`.

В панели действий владельца видны причины неполноты данных шлюза с ID задачи и ожидания модели. Повреждённое чтение сохраняет прежние сведения с предупреждением; исправление API снимает пробел. Диагностика учитывает текущую комнату и не создаёт управляющих действий. Проверка: `npm run test:attention-gaps:gjs`.

В расходах задачи отдельно показаны резерв ещё не отправленных вызовов и верхняя граница вызовов без известной цены, с областью этих данных. Нарушенная или неизвестная целостность журнала видна и в деталях, и рядом с краткой суммой. `npm run test:task-cost-openness:gjs` проверяет настоящий task API и учёт, включая карантин повреждённой строки журнала.

В окне задачи доступны сохранённые сведения об остановке: источник, область, причина, время, ID запроса и записанная команда Stop now/Wrap up. Задача, связанная с запросом, показана отдельно от явно записанного инициатора; HTTP-клиент не объявляется владельцем. Проверка: `npm run test:task-stop-origin:gjs`.

Окно задачи также показывает текущую сверку делегированных запусков: несверенные записи, открытые запуски, ожидающие запросы/решения по патчам и все опубликованные итоговые квитанции. Пока сверка не завершена, окно перечитывает API; после подтверждённой очистки опрос прекращается. Проверка: `npm run test:task-reconciliation:gjs`.

Из квитанции можно открыть и скачать сохранённый ответ через Files, если шлюз опубликовал явный абсолютный адрес внутри разрешённого файлового корня. Чтение проверяет размер/SHA‑256 и сохраняет привязку к корню до закрытия просмотра. Частичный ответ отмечен отдельно; просмотр не подтверждает его потребление агентом. Проверка: `npm run test:retained-output:gjs`.


Одноразовые события шлюза показываются нативными Toast с полным текстом в отдельном диалоге и переходом к задаче. Повторы после переподключения подавляются; новые уведомления ждут закрытия модального окна. Проверка: `npm run test:gateway-notices:gjs`.

Сообщения об операциях навыков раскрывают записанное состояние, исходный чат и связанные задачи. Повторный запрос показывает ссылку на существующую операцию; синтетический ID потока не используется как задача. Проверка: `npm run test:skill-progress:gjs`.

Чат и окно задачи показывают записанный выбор усилия при отправке: запрошенное значение, выбранное значение и источник решения. Маршрут и основа учёта координатора показаны отдельно от сохранённого родительского маршрута и наблюдений об исполнителе. В деталях сообщения также доступны опубликованные число активных субагентов, лимит и признаки ожидания свободного места на момент планирования. Эти наблюдения не объявляются текущей загрузкой или подтверждением запуска. Проверка: `npm run test:dispatch-facts:gjs`.

В событиях задачи есть нативная сводка контрольных точек контекста, бюджета и сервисов. Повторные записи одного ожидания объединяются по задаче и ID эпизода; неизвестная длительность отличается от нулевой. Сводка ограничена выбранными источниками и сохранённым окном событий. Проверка: `npm run test:task-checkpoints:gjs`.

Напоминания расписаний появляются в приложении как нативные Toast. В деталях сохранены полный подписанный текст и опубликованные даты записи, назначения и доставки. Повтор после переподключения подавляется; напоминание не создаёт задачу. Проверка: `npm run test:reminder-notices:gjs`.

Реплики вызова показывают записанный статус речи: сгенерирована, воспроизведена или прервана, с подтверждёнными миллисекундами. Live-квитанция связывается с точным сообщением; если chat history её не публикует и локальной квитанции нет, статус остаётся неизвестным. Сохранённые квитанции читаются в деталях событий задачи. Проверка: `npm run test:spoken-receipt:gjs`.

Форма защиты материалов отдельно показывает квитанцию операции и перечитанное текущее состояние защиты. При потере ответа POST не повторяется автоматически; частичное освобождение, неизвестные материалы и занятое хранение не выдаются за полный успех. Проверка: `npm run test:owner-keep:gjs`.

Нативный клиент GTK4 + Libadwaita для шлюза [Ouroboros](https://github.com/razzant/ouroboros). Интерфейс работает на GJS, консольный клиент — на Node 26.

## Установка (рекомендовано)

Релизные бандлы собираются автоматически на GitHub: пуш тега `v*` → workflow `flatpak` → `.flatpak` в Release. Скачай свежий `ouroboros-client-v*.flatpak` со страницы Releases и поставь:

```sh
flatpak install --user ./ouroboros-client-vX.Y.Z.flatpak
flatpak run io.github.ouroboros.Client
```

Рантаймы: `org.gnome.Platform//51`, `org.gnome.Sdk//51` (ставятся автоматически как зависимости).

## Сборка вручную

Для локального `npm run build` вне Flatpak нужны Python 3, C-компилятор, pkg-config, заголовки GLib/GIO и gobject-introspection (`g-ir-scanner`, `g-ir-compiler`). Сборка создаёт небольшой GIO-модуль для потоковой передачи HTTP в WebKit. При сборке Flatpak эти инструменты предоставляет GNOME SDK.

```sh
flatpak-builder --user --install --force-clean build-dir io.github.ouroboros.Client.json
flatpak run io.github.ouroboros.Client
```

(`--disable-rofiles-fuse` нужен только в контейнерах без /dev/fuse, на обычном хосте — без флага.)

## Настройка подключения

Шестерёнка в шапке открывает настройки адреса шлюза, сетевого пароля и чата при запуске. Кнопка «Проверить подключение» показывает, отвечает ли шлюз, принят ли доступ к защищённому состоянию и готов ли супервизор. Настройки хранятся в `~/.config/ouroboros-client/settings.ini`. Для Flatpak этот каталог находится внутри `~/.var/app/io.github.ouroboros.Client/config/`. Переменные окружения `OUROBOROS_URL` и `OUROBOROS_NETWORK_PASSWORD` задают исходные значения. ID стартового чата сохраняется без 32-битного ограничения, в диапазоне безопасных целых JavaScript. Закрытие окна или изменение адреса отменяет проверку. Сохранение настроек того же шлюза сохраняет открытый cookie-сеанс; вход на сеанс очищает поле пароля и сохраняет пустой пароль. Проверка окна: `npm run test:connection-settings:gjs`.

В файловом браузере ошибки и неполные ответы сохраняют последний прочитанный список с предупреждением. Переход в другую папку отменяет прежнее чтение; закрытие страницы отменяет чтения, выбор файла и скачивание. Закрытие редактора во время проверки текущей версии отменяет проверку до записи. Проверка: `npm run test:files-browser:gjs`.

Редактор подтверждает сохранение только при совпадении пути и точного размера UTF‑8 текста в квитанции шлюза. Неполная, противоречивая или потерянная квитанция сохраняет черновик и предлагает проверить содержимое на шлюзе без повторной записи. Проверка: `npm run test:file-write-receipt:gjs`.

Загрузка файла сверяет имя, папку назначения и размер квитанции с фактически отправленными байтами. Если ответ потерян или противоречив, клиент сообщает, что файл мог сохраниться; перед явным повтором можно обновить папку. Автоматического повтора загрузки нет. Проверка: `npm run test:file-upload-receipt:gjs`.

Upload и скачивание сохраняют объявленный корень на момент выбора действия. После системного выбора файла/назначения клиент перечитывает исходную папку до передачи байтов; окно просмотра сохраняет собственный контекст для скачивания даже после навигации основного списка. Отказ проверки оставляет локальное назначение прежним; отмена и закрытие отменяют проверку до передачи. Проверка: `npm run test:file-io-root:gjs`.

Выбор папки на шлюзе поддерживает ввод абсолютного пути, переход вверх/домой и повторное чтение. Если шлюз ограничил список первыми 500 папками, путь к другой папке можно ввести вручную. Ошибка сохраняет прежний список с предупреждением; выбор доступен после успешного чтения. Изменение пути и закрытие формы отменяют запросы. Проверка: `npm run test:directory-picker:gjs`.

Для шлюза с сетевой авторизацией кнопка «Войти на этот сеанс» обменивает пароль на cookie шлюза. Cookie хранится в памяти до закрытия клиента или команды «Завершить сетевой сеанс» в шапке окна.

Если шлюзу нужна первичная настройка, клиент открывает мастер GTK. Из настроек шлюза мастер можно вызвать вручную. Если связь оборвётся при сохранении, «Проверить квитанцию» запрашивает результат той же попытки. ID неопределённой попытки сохраняется локально без черновика и ключей; новая сессия мастера сначала проверяет её квитанцию. Закрытие отменяет запросы и очищает поля паролей. Неполный каталог начальных навыков сохраняет прежний выбор. Проверка: `npm run test:onboarding:gjs`.

В «Моделях» можно проверить окно контекста и максимальный ответ для маршрута выбранной роли или отдельной резервной модели. Подтверждение и отзыв применяются к отпечатку, который вернул шлюз. В «Веб-поиске» можно проверить порядок встроенных маршрутов и причины их недоступности до сохранения настроек.

«Настройки вызовов» открываются из чата и из разделов навыка `live_conversation`. В окне можно включить бета-режим, выбрать движок, модель и голос и настроить доступные для модели параметры. Если ответ на запись потерян, кнопка «Перечитать» сверяет выбор с сохранёнными настройками. После подтверждения готовности шлюзом появляется кнопка «Позвонить». Звук проходит через GStreamer и PulseAudio, в том числе через PipeWire с PulseAudio-совместимым сервером.

«Функция вызова» позволяет выбрать зарегистрированную функцию другого навыка из списка шлюза. Её параметры открываются через «Настройки функции». Выбор действует в текущем сеансе клиента. При исчезновении функции из списка или ошибке чтения клиент сохраняет выбор и блокирует новый запуск до подтверждения доступности. Окончательную готовность проверяет шлюз при открытии. Если в комнате уже идёт разговор, шлюз может подключить к нему; это отдельно отмечается в панели.

Во время разговора «Контекст вызова» передаёт дополнительный факт собеседнику. В этом же окне можно вручную указать имя участника и сообщить, говорит ли он сейчас. Форма привязана к выбранному вызову; после его завершения или замены текст остаётся доступен для копирования, а отправка блокируется. Повторная передача при потере ответа не выполняется автоматически.

Если шлюз разрешает изображения в вызове, рядом с управлением микрофоном появляются кнопки камеры и демонстрации. Клиент запрашивает доступ через портал рабочего стола и получает выбранный видеопоток через PipeWire.

В диалоге «Устройства вызова» можно выбрать микрофон, аудиовыход и камеру, настроить шумоподавление и автоматическое усиление микрофона. Запрос эхоподавления выполняет аудиосервер. Настройки сохраняются локально. При отключении выбранного устройства клиент пробует перейти на системное.

В чате «Движок диктовки» показывает доступные серверные движки распознавания и место обработки аудио. После выбора можно записать фразу с системного микрофона. Клиент отправляет запись в поддерживаемом движком формате, соблюдая лимиты размера и длительности. Распознанный текст добавляется в черновик. Если черновик изменился, результат можно вставить вручную или скопировать.

Когда на шлюзе включён навык «Голос устройства» (`device_voice`), ответы можно прочитать вслух. eSpeak NG синтезирует речь локально, а GStreamer воспроизводит её через системный аудиовыход. Flatpak включает eSpeak NG. При запуске из исходников `espeak-ng` должен быть доступен в `PATH`. Исполняется проверенная ревизия JS-модуля навыка; она получает локальные голоса и воспроизведение через нативный Web Speech synthesis адаптер. Отдельного обхода по имени `device_voice` нет. Движок и голос сохраняются в настройках шлюза, а список голосов определяется локальным синтезатором.

Группы компонентов поддерживают вертикальный порядок, сетку и компактный ряд с переносом. Формы учитывают число столбцов и ширину поля `span`. В узком окне поля располагаются в один столбец, сохраняя ввод и фокус. У форм виджетов и настроек навыков нет ограничений карточек на 50 полей и 4000 символов. Числовые поля проверяют десятичную запись, диапазон и шаг до отправки; база шага учитывает минимум и исходное значение. Регрессионная проверка форм запускается командой `npm run test:forms`. Email и URL проверяются до отправки с нормализацией адресных пробелов; текст и пароли не меняются. Проверка GJS-парсера по сохранённой матрице WebKit запускается через `npm run test:forms:gjs`.

Mermaid в ответах чата и итогах проектов отображается как SVG средствами GTK/librsvg. Доступны масштаб, прокрутка, охват по ширине, копирование исходника, сохранение SVG и нативные ссылки. Расчёт схемы выполняет локальный служебный WebKit с отдельным контекстом и временным сеансом; отображение и управление принадлежат GTK. Расчёт не обращается к шлюзовому веб-интерфейсу или CDN. При ошибке остаётся читаемый исходник. Изображения узлов загружаются нативно и включаются в экспортируемый SVG; файлы текущего шлюза используют его авторизацию, внешние адреса — отдельный сеанс без неё. PNG/JPEG/GIF/WebP и SVG преобразуются в PNG. Изображения внутри HTML-подписей узлов и связей также преобразуются в SVG с сохранением текста и ссылок. Внешние шрифты/стили, адаптивный `srcset` и другое вложенное медиа пока недоступны. Проверки: `npm run test:mermaid:gjs` и `npm run test:diagram-images:gjs`.

Формулы ответов и итогов проектов отображаются средствами KaTeX 0.17 → MathML → MathJax SVG → librsvg/GTK: строчные `\(…\)`, отдельные `$$…$$` и `\[…\]`, включая вложенные цитаты и таблицы. Поддержаны дроби, индексы, суммы/интегралы, матрицы, системы и химические формулы. По нажатию на формулу доступен её TeX и копирование; при ошибке остаётся исходник. Рендеринг локальный, учитывает тему и масштаб GTK. Разбор соответствует KaTeX шлюза; глобальные макросы сохраняются между формулами одного ответа и изолированы от других сообщений. Подготовка в исходном порядке сохраняет смысл макросов при перелистывании таблиц. Выступающие части правил и поднятых символов не обрезаются. Шрифты и интервалы SVG могут отличаться от веб-клиента. Проверки: `npm run test:math`, `npm run test:math:gjs`.

Ответы в чате и итоги проектов показывают Markdown средствами GTK. Переносы строк сохраняются, исходный HTML виден как текст; сообщения владельца сохраняют исходный вид с активными HTTP/HTTPS-ссылками. Изображения Markdown представлены ссылками без автоматической загрузки. Ссылка на файл шлюза открывает нативный просмотр и сохранение с авторизацией текущего подключения. Сообщение и блок кода можно скопировать целиком.

Блоки `chart` в Markdown рисуются нативно через Cairo/Pango: линии, столбцы, круговые и кольцевые диаграммы, полярные и радарные графики, точечные и пузырьковые диаграммы. Есть подсказки точек, переключение рядов через легенду, смена темы и размера, таблица исходных данных и просмотр JSON. Компонентные графики также используют этот рендерер; данные больше не обрезаются до 200 точек и 24 рядов. Проверки: `npm run test:charts` и `npm run test:charts:gjs`.

Блоки кода в Markdown и компоненты `code` используют GtkSourceView 5: подсветку синтаксиса, автоопределение языка и цвета светлой/тёмной темы. Содержимое остаётся доступным для выделения и точного копирования. При запуске из исходников для подсветки нужен GtkSourceView 5; Flatpak получает библиотеку и языковые схемы из GNOME Platform 51. Проверки: `npm run test:code` и `npm run test:code:gjs` (для второй нужны Xvfb и D-Bus).

Markdown в карточках, декларативных виджетах и настройках навыков отображается средствами GTK: заголовки, выделение, списки, цитаты, код, ссылки, таблицы и раскрывающиеся блоки. Исходник и код можно скопировать. Большие таблицы доступны по страницам. Проверка разбора запускается через `npm run test:markdown`.

Карты карточек и декларативных виджетов отображаются через libshumate: фон `tiles_url`, маркеры с подписями и описаниями, масштаб, перемещение, выбор точки и охват всех точек. Без фона остаются координаты и маркеры. Полный список доступен отдельно, включая записи с неподходящими координатами. Обновление данных виджета сохраняет положение карты; скрытие и закрытие снимают слой загрузки. Транспорт тайлов отделён от авторизации шлюза. Flatpak включает libshumate 1.7; для запуска из исходников нужен typelib `Shumate-1.0`. Проверки: `npm run test:maps` и `npm run test:maps:gjs`.

Списки календаря, маркеров карты и пар ключ–значение доступны целиком по страницам. Канбан показывает все колонки и карточки с отдельной навигацией; неизвестная колонка не скрывает её карточки. В виджете с `on_move` можно перемещать и карточки без явного ID — используется правило шлюза по колонке и исходной позиции. Выбранное назначение сохраняется при перелистывании; пока запрос выполняется, доска блокирует повторную отправку. В обычных карточках канбан доступен для чтения.

Таблицы карточек и виджетов открывают ссылки HTTP/HTTPS, форматируют числа с единицами и показывают стили статусов. Относительные ссылки разрешаются от адреса шлюза. Большие таблицы доступны целиком через отдельное переключение страниц строк и столбцов; текущее положение показано над таблицей.

Галереи карточек и декларативных виджетов показывают весь список по 20 файлов на странице, с подписями и отдельным альтернативным текстом изображений. При перелистывании освобождаются плееры и временные файлы, отменяются незавершённые загрузки. Обновление списка сохраняет номер страницы в доступных пределах; изменение данных обновляет и источники статических элементов. Маршруты `items_key`/`route_prefix` поддерживают имена файлов с пробелами и специальными символами. Проверка GTK: `npm run test:galleries:gjs`.

Карточки с декларативными компонентами воспроизводят встроенные аудио и видео через GTK, в том числе внутри галерей. Медиа можно сохранить локально. При смене вкладки воспроизведение приостанавливается; закрытие или обновление карточки освобождает временные файлы.

Декларативные элементы навыков появляются в меню «+» поля ввода, в ряду индикаторов и рядом с сохранёнными ответами. Они могут вставлять шаблоны, выполнять запросы к навыкам, показывать уведомления и открывать карточку навыка на доске виджетов. В пункте «Элементы навыков» можно изменить порядок или скрыть отдельные элементы. Шлюз хранит эту настройку.

Нажатие на цитату открывает исходное сообщение в истории, в том числе в другом проекте. В деталях задачи «Параметры переноса» позволяет задать ID проекта, название и исходный запрос владельца как подсказку для названия. Быстрое создание проекта остаётся отдельной кнопкой. Повтор после потери ответа сохраняет параметры в текущем сеансе; после подтверждения привязки повтор квитанции уже не отправляет имя заново. Если полный снимок подтверждает отсутствие привязки, параметры можно исправить с восстановлением прежних значений. Неполный снимок не разрешает повтор. Закрытая форма параметров не отправляет запрос. Проверка: `npm run test:project-handoff:gjs`.

В деталях задачи есть переход к её записи в чате. Кнопка «К последним сообщениям» возвращает к текущей переписке. Когда шлюз выдаёт курсор новых записей, клиент обновляет историю по нему.

В обзоре «Активность» собственные пробуждения и пробуждения в местах показаны отдельно. Из карточки можно открыть запись в Main или сохранённую историю конкретного разговора места. Время первого ответа или автоматического выпуска, аккаунт фокуса, проверки и расходы показаны по данным шлюза.

Ошибка отдельного раздела обзора сохраняет его прежние сведения с предупреждением. Неполные ответы не подменяют последний снимок. Новое чтение отменяет предыдущее; уход с обзора и закрытие приложения отменяют оставшиеся запросы. Старые кнопки фоновой работы не отправляют команды после ошибки или перерисовки. Проверка: `npm run test:activity-overview:gjs`.

История комнат показывает Markdown нативными GTK-виджетами, когда шлюз явно пометил сообщение как форматированное; обычный текст остаётся дословным. Предыдущие страницы сохраняются при ошибке чтения. Закрытие окна отменяет запросы, повторённые курсоры не создают бесконечную ленту, а смена представления истории возвращает к актуальной последней странице. Проверка: `npm run test:place-history:gjs`.

Страница истории проверяется целиком перед показом: вложенные сведения о доставке, реакции, импорте, удержанном тексте и снимке аккаунтов. Ошибка сохраняет последние прочитанные страницы с явной отметкой неподтверждённого обновления. Неизвестные строковые коды и пользовательские факты показываются как данные; старые снимки аккаунтов совместимы.

В «Активность → Расходы» видны известные расходы, общий лимит, резервы и вызовы без цены. Если шлюз вернул разбивку для основной задачи и её подзадач, в деталях задачи можно посмотреть расходы по назначению и маршруту, включая сессии по подписке.

В «Активность → API» можно посмотреть контракт подключённого шлюза, найти HTTP-маршрут или сообщение WebSocket, перейти к схеме запроса или ответа и сохранить полный JSON.

В «Активность → Ревью» можно запросить глубокое ревью всей системы и выбрать основную модель Main или включённого субагента. Клиент сверяет маршрут выбранного субагента перед отправкой.

В «Настройки шлюза → Субагенты» можно менять состав и порядок каталога, маршруты, права сессий и участие в пуле ревью. Когда шлюз требует подтверждения пустого пула, форма запрашивает его отдельно.

Из каталога и окна аккаунтов можно открыть сохранённый пул ревью. Для каждого участника видны измеренная стоимость и последнее выполнение с отдельными сведениями о запрошенном и фактическом маршруте.

В «Настройки шлюза → Политика ревью» можно выбрать влияние замечаний, режим проверки результата задачи и предел оплачиваемых циклов. Шлюз сообщает политику текущего процесса и следующей задачи, а окно показывает, как на неё влияет Cyber Pro.

Маршрут субагента можно выбрать из каталога моделей шлюза. Для сессии Claudexor доступны инструмент, модель и конкретный аккаунт либо автоматический выбор аккаунта.

В редакторе каталога можно запросить предложенный состав по настройкам моделей или с учётом подключённых подписок. Выбранный состав и предложенные назначения моделей переносятся в черновик перед отдельным сохранением.

Если новые назначения меняют маршрут Safety Supervisor, шлюз требует подтверждение владельца. Остальные правки остаются в форме для отдельного сохранения.

В «Субагенты → Выполнения субагентов» виден последний сохранённый запуск для каждой строки. Экран сравнивает параметры запуска с текущим составом, отдельно показывает запрошенную, фактическую и резервную модель и позволяет открыть связанную задачу.

В «Субагенты → Доступность маршрутов» видны сведения шлюза об инструментах, аккаунтах и квоте для маршрутов из открытой формы. Квота подтверждается только при совпадении области проверки шлюза с выбранной моделью и подходящим аккаунтом. Доступность API-моделей проверяется при запуске.

В окне «Аккаунты Claudexor» для каждого аккаунта можно открыть сведения о доступе к моделям и увидеть временные отметки, причины и срок до повторной проверки. Окно показывает выбранный шлюзом следующий аккаунт или маршрут с ключом API, когда список аккаунтов актуален.

В «Обновлениях шлюза» план и окно подтверждения показывают проверки выбранного диапазона. Для каждого коммита видны квитанция и сведения о ревью. Отдельный список показывает запуски GitHub после слияния, их охват и коммиты без сопоставленного запуска.

Перед подтверждением обновления клиент показывает, сохранится ли запущенный Claudexor, какие операции движка были активны на момент проверки и какие версии Python и SQLite установлены на шлюзе. Последствия слияния и замены официальной версией отображаются отдельно.

В подробностях последней попытки обновления видны сохранённый исход и замеры процесса шлюза до и после обновления. При наличии данных можно открыть задачу, для которой шлюз замерил время от приёма сообщения до первого вызова модели.

При незавершённом обновлении окно показывает, можно ли запросить перезапуск для проверок при запуске или восстановление требует отдельного перезапуска процесса шлюза. Клиент перечитывает фазу транзакции после подтверждения команды.

Для отката можно выбрать локальный коммит или тег, указать полный SHA либо перейти прямо к версии до последнего успешного обновления. Официальные релизы, полученные при проверке, видны отдельно.

Статус обновлений показывает источник и ветку, расхождение истории и изменения содержимого рабочей копии. Клиент выводит причину сбоя и время последней успешной проверки, когда шлюз возвращает эти сведения.

В описании обновления видны его диапазон, состояние задачи и факт сохранения текста. При потере ответа клиент сверяет запрос с записью на шлюзе. Из панели можно открыть текущую попытку задачи описания.

Сохранённое описание отображает Markdown нативными GTK-виджетами, включая заголовки, таблицы и блоки кода; исходный Markdown доступен отдельно. Видны модель и задача автора, если они указаны шлюзом. Собранные материалы и проверки коммитов доступны отдельно с собственными диапазонами.

В настройках встроенного веб-поиска можно проверить порядок источников Auto, выбрать источник и модель, указать именованное подключение. Шлюз сообщает рекомендуемые модели и причины недоступности маршрутов. Предпросмотр не вызывает поиск и не сохраняет настройки: кнопка применения переносит выбор в основную форму. При ошибке чтения прежний маршрут остаётся с предупреждением; изменение выбора убирает устаревший предпросмотр. Закрытие настроек отменяет чтение и закрывает окно поиска. Проверка: `npm run test:web-search:gjs`.

В обзоре «Активности» можно запустить кампанию саморазвития с целью, изменить цель действующей кампании или остановить её. Состояние и ссылки на задачи поступают со шлюза. В «Версиях» доступны контрольные точки циклов и замеры журналов памяти для каждого выпуска.

Перед отправкой выбранный профиль перечитывается; изменение маршрута, материалов или перепроверки требует нового выбора. Если начальный каталог недоступен, Main предлагается явно. Ошибка проверки уже выбранного профиля не заменяет его на Main. Закрытие отменяет загрузку и выбор. Проверка: `npm run test:system-review:gjs`.

Запуск требует подтверждённых режима, готовности supervisor и состояния кампании. Закрытый диалог цели не отправляет команду по позднему ответу; смена ID кампании делает прежнее предложение недействительным. Принятие команды не выдаётся за её выполнение. После неизвестного результата запуска клиент ждёт отдельного чтения состояния и не повторяет POST автоматически. Проверка: `npm run test:evolution-campaign:gjs`.

В «Навыки → ClawHub» можно настраивать выборку реестра, просматривать сведения о плагинах и выбирать выпуск. Квитанция установки или обновления показывает версию и контрольную сумму архива, замечания проверки и результат подготовки зависимостей.

Изменение выпуска обезвреживает прежнюю кнопку установки; перечитывание установленных навыков — прежние действия обновления и удаления. Закрытие окна отменяет чтение карточек и предпросмотров. Потерянный ответ операции показывается как неизвестный исход; клиент не повторяет POST автоматически. Проверка `npm run test:skill-registry:gjs` выполняет установку, обновление и удаление локального тестового архива через настоящую lifecycle-очередь. Реестр и вердикт ревью в этом стенде синтетические.

В карточке установленного навыка «Разделы настроек» открывает его формы и действия в GTK. Если маршрут принимает запись, но не выдаёт сохранённые значения, заполнение формы начинается с отдельной кнопки «Редактировать без чтения».

«Попросить исправить» отправляет отдельную команду для выбранной копии навыка. Каждая подтверждённая отправка получает новый идентификатор корреляции. Сообщение о приёме команды означает запуск обработки; результат исправления нужно смотреть в задачах и чате. При потере ответа клиент предлагает проверить их перед повтором. В историю передаётся краткая запись запроса. Её идентификатор корреляции не отображается как ссылка на задачу; задача получает отдельный ID от шлюза.

«Процессы навыков» обновляет снимок фоновых процессов шлюза. Из карточки можно открыть процессы конкретного навыка и посмотреть сохранённые наблюдения сервера и рабочего процесса, включая причину исчерпания перезапусков.

В мониторе есть локальный поиск по навыку, имени, PID, заявленному порту и причине остановки. Фильтрация сохраняет развёрнутые строки. При ошибке чтения остаётся последний снимок с предупреждением; закрытие родительского окна отменяет чтение и периодическое обновление. Проверка: `npm run test:skill-processes:gjs`.

В «Навыки → Источники» можно выбрать папку на шлюзе или проверить Git-репозиторий с веткой и подпапкой. Для Git можно закрепить коммит, прочитанный при проверке. Каталог сохраняет результаты поиска при обновлении списка источников и позволяет выделить официальные или рекомендованные навыки.

Окно обновления установленного навыка показывает квитанцию пропуска или объединения и следит за операцией замены. Если запись очереди содержит ID задачи, её можно открыть из списка операций с навыками.

В очереди операций навыков раскрываются источник, времена, сообщения/ошибки, возраст и stale-подсказка шлюза, чат прогресса и роли связанных задач. Панель проверки навыков (chat 0) отличается от Main (chat 1). При ошибке чтения остаётся предыдущий снимок с предупреждением и без переходов. Записи очереди хранятся в памяти; исчезновение старой записи не подтверждает исход операции. Проверка: `npm run test:skill-lifecycle:gjs`.

При публикации навыка клиент повторно сверяет условия перед отправкой и сохраняет ID задачи и выбранный репозиторий. Если ответ потерян, квитанцию можно проверить после перезапуска GNOME-клиента и открыть подтверждённую задачу.

В деталях задачи публикации можно прочитать журнал попыток и увидеть последний подтверждённый этап. Ссылки на pull request из журнала и карточки навыка проверяются по репозиторию и номеру.

В разделе «Файлы» квитанция копирования или перемещения сохраняется при переходе в другую папку. При конфликте можно выбрать другое назначение. После потери ответа можно проверить исходную папку и назначение отдельными запросами.

Копирование, перемещение, удаление и создание папки сохраняют объявленный корень исходного списка и проверяют его перед POST. Смена корня во время подтверждения или выбора назначения останавливает действие до отправки. При сверке потерянного ответа списки из другого корня помечаются неподтверждёнными. Проверка: `npm run test:file-actions-root:gjs`.

Новый текстовый файл создаётся при первом сохранении черновика. При конфликте редактор показывает текущую версию на шлюзе рядом с черновиком. После потери ответа можно перечитать файл и сверить его с текстом в редакторе.

Редактор запоминает объявленный шлюзом корень файлов и путь прочитанной цели. Если корень или цель символической ссылки изменились, сохранение и сверка потерянного ответа останавливаются с сохранением черновика. Новый файл дополнительно проверяет корень родительской папки. Это проверка перед запросом записи; API не предоставляет атомарного условия на корень. Проверка: `npm run test:file-root:gjs`.

В «Расписаниях» после потери квитанции кнопка «Проверить запись на шлюзе» ищет расписание по тому же ID. Если исходное состояние сохранилось, можно повторить отправку с теми же данными. Из деталей расписания открываются предыдущий незавершённый запуск и исходная задача, если шлюз указал их ID.

Редактор расписания использует язык интерфейса шлюза. Смена языка и обновление переводов сохраняют текст, JSON, время, назначение и выбранное усилие, включая неизвестное клиенту значение. Названия проектов, текст задания и другие введённые данные не становятся исходниками переводов. Проверка: `npm run test:schedule-i18n:gjs`. Список, детали, формы действий и квитанции также обновляются при смене языка, сохраняя фильтр, причину и выбранную связь с исходной задачей. Проверка: `npm run test:schedule-page-i18n:gjs`.

В окне ревью видны версии плана, критерии завершения, открытые и отозванные возражения. Из истории чата окно открывается по записи «План и ревью». Сохранённую реплику участника можно прочитать и скачать после проверки контрольной суммы.

Закрытие ревью закрывает вложенные документы и отменяет их чтение, выбор файла и запись. После ошибки записи можно повторить сохранение проверенного текста; старые кнопки закрытого документа не запускают запросы. Проверка: `npm run test:task-reviews:gjs`.

Материалы задачи показывают имя, размер и SHA-256. Файл больше 1 МиБ скачивается по отдельному нажатию без загрузки в текстовый просмотр. Перед сохранением проверяются размер и контрольная сумма. Для локального назначения готовая копия заменяет прежний файл переименованием из той же папки; ошибка передачи или отмена до замены сохраняют прежний файл. Проверка: `npm run test:task-artifacts:gjs`.

Список задач объединяет сохранённые записи и снимок очереди, поддерживает серверные фильтры состояний, полный список без лимита и локальный поиск. Фильтр текущего проекта учитывает подтверждённую привязку. Неполные сведения об очереди помечаются отдельно; ошибка повторного чтения сохраняет прежнюю выдачу того же запроса. Закрытие обезвреживает действия и отменяет чтение. В режиме «Только очередь» активная страница обновляется каждые 10 секунд. Проверка: `npm run test:task-inventory:gjs`.

Основная карточка задачи скачивает вложенные файлы по точному относительному пути и предлагает архив записанного каталога. Выбор назначения связан с карточкой: повторное нажатие не создаёт вторую операцию, закрытие отменяет выбор и скачивание. Успех виден в карточке, ошибка открывается поверх неё. Проверка: `npm run test:task-artifact-detail:gjs`.

В деталях задачи показаны наблюдения при завершении и сохранённые материалы приёмки. Ответ инструмента о результате вызова отображается отдельно от сведений о доставке. Материалы до 1 МиБ можно просмотреть в окне клиента. При скачивании более крупных материалов клиент проверяет размер и SHA‑256 перед записью в выбранный файл.

В чате для делегированных запусков видны сообщения, итоговый ответ, технические события и пропуски журнала. Сохранённые диапазоны журнала открываются и скачиваются как JSONL с проверкой SHA‑256. В деталях задачи можно увидеть запрошенный маршрут, наблюдения исполнителя и подтверждённые сведения о завершении.

В списке комнат видны счётчики непрочитанных сообщений. Отметки Main и проектов хранятся на шлюзе и синхронизируются между клиентами. При открытии непрочитанной комнаты клиент показывает последнее сообщение, названное шлюзом. Полностью просмотренное общее сообщение уменьшает счётчик и в других комнатах, где оно опубликовано.

В чате можно менять контекст, основное усилие, диапазон усилия субагентов и режим их запуска для Main или открытого проекта. Если в этой комнате ещё сохраняются настройки, отправка ждёт ответа шлюза. При отказе или неподтверждённом результате сообщение остаётся в черновике. В деталях задачи «Роя» можно посмотреть подтверждённые и отклонённые запуски из отчёта шлюза.

Если шлюз предложил выбрать назначение сообщения, «Маршрут сообщения…» открывает нативный выбор с комментарием. Перед отправкой клиент проверяет сохранённую запись и токен маршрута. После потери ответа можно проверить историю без повторной отправки; переходы к проекту и задаче появляются по адресам квитанции. Закрытые окна и старые элементы после перерисовки не выполняют переходы. Проверка: `npm run test:routing-picker:gjs`.

Передача сообщения существующей задаче сохраняет исходные слова как цитату владельца и не меняет усилие задачи. Если отправка по маршруту осталась неподтверждённой, «Повторить прежний запрос» использует прежние вариант, комментарий и ID запроса, в том числе после закрытия и повторного открытия окна в том же сеансе. Проверка: `npm run test:routing-replay:gjs`.

Неподтверждённые запросы маршрутизации сохраняются до отправки в локальном журнале с правами `0600`, отдельно для шлюза и комнаты. После перезапуска клиента повтор остаётся ручным и сначала сверяет сохранённый маршрут. Подтверждённые и заменённые решения удаляются при свежем чтении; закрытие окна сохраняет незавершённый запрос. Если журнал повреждён или недоступен для записи, клиент не делает POST поверх несохранённого состояния. Проверка двумя отдельными процессами: `npm run test:routing-journal:gjs`.

Связка маршрута с сообщением в основном чате и панели проекта проверяется через настоящий `ChatSocket` и историю шлюза: `npm run test:chat-routing:gjs`. Действия маршрута не очищают поля обычных сообщений; пересоздание страниц восстанавливает ручной повтор из журнала, а подтверждение в истории убирает незавершённую запись.

Main принимает живые события внешних переписок с положительным chat_id, сохраняя изоляцию проектов по серверной метке project_thread и реестру. Файлы и индикаторы набора разделены по исходным чатам; обычный одноразовый typing-индикатор истекает, сведения о работе берутся из `/api/state`. Проверка настоящего WebSocket/bridge/history и совпадения правил выбора потока с эталонным клиентом: `npm run test:chat-room:gjs`.

Подписи и состояния маршрута используют язык интерфейса шлюза. Смена языка сохраняет выбранный вариант и комментарий; перевод не меняет идентичность запроса в журнале. Названия вариантов, файлы и объяснения из ответа шлюза показываются дословно и не отправляются в очередь переводов. Проверка: `npm run test:routing-i18n:gjs`.

Неполные данные маршрута не заменяют прежнее представление. Если точную запись не удалось проверить, отправка остаётся недоступной, а комментарий сохраняется. Противоречивая квитанция не подтверждает отправку и не открывает непроверенную задачу; результат можно перечитать без повторной отправки. Проверка: `npm run test:routing-protocol:gjs`.

В «Активности» показана работа всех комнат, а в чате можно развернуть список для текущей комнаты. Кнопки используют цели, которые указал шлюз. Можно остановить прежнюю попытку или всю связанную работу, поставить её на паузу, ускорить, завершить с частичным результатом или возобновить, если шлюз разрешил действие. При неполном снимке пропавшие работы остаются в списке со статусом «Не подтверждено».

«Текущие вопросы» в чате и «Активности» открывают вопросы, даже если их сообщений нет на загруженной странице истории. Перед открытием формы клиент проверяет вопрос и его комнату по данным задачи. При неполном снимке вопросы с неподтверждённым статусом остаются в списке с недоступной кнопкой.

В разделе «Доступ к моделям и действия владельца» можно повторно проверить доступ, выбрать модель и аккаунт из каталога, настроить автоматическое возобновление или начать вход заново. Клиент отдельно показывает принятие запроса шлюзом, его применение задачей и результат сохранения роли в настройках. Раздел доступен в чате, «Активности» и деталях задачи.

У отправленного сообщения чат показывает квитанцию маршрутизации и ссылки на проект или задачи, которые назвал шлюз. Если в истории сохранилась карточка выбора маршрута, из неё можно отправить исходное сообщение в существующую задачу или создать задачу в проекте. При неопределённом результате повтор в текущем сеансе сохраняет прежний вариант, комментарий и идентификатор запроса.

Чат показывает отдельно сохранение сообщения шлюзом и начало передачи в обработку. Отправку без подтверждения можно восстановить после перезапуска клиента и повторить с теми же текстом, цитатой, вложениями и идентификатором. Если сообщение сохранено, а состояние передачи неизвестно, его текст можно перенести в новый черновик.

Кнопка «Найти проект» открывает полный список проектов шлюза с поиском по названию, ID и номеру комнаты. Точный адрес можно проверить отдельно, даже если список временно недоступен. Список показывает страницы по 50 записей, закреплённые проекты и счётчики непрочитанного. Поиск учитывает Unicode и диакритику. Неполный ответ сохраняет прежний список с предупреждением; удаляющийся проект виден без перехода в его комнату. Закрытие отменяет точный поиск, а закрытие клиента — чтение полного списка. Проверка: `npm run test:project-directory:gjs`.

Окно удаления проекта следит за записью в реестре. Оно показывает приём запроса, отмену задач и ошибки завершения. При ошибке можно повторить удаление того же проекта. При потере ответа окно перечитывает состояние по ID. Неполный снимок оставляет прежнее состояние видимым и блокирует удаление. Закрытие отменяет чтение и подтверждение, останавливает периодические проверки. Открывается одна форма удаления. Проверка: `npm run test:project-deletion:gjs`.

Из деталей задачи можно перенести её в проект. Клиент показывает привязку задачи и состояние квитанции для Main отдельно. Если ответ потерян, «Проверить привязку на шлюзе» читает актуальное состояние задачи. Проверка доступна и после повторного открытия деталей в том же сеансе. В Main связанные записи о переносе дают один переход в проект.

В Main ответ завершённой задачи проекта показан вместе с подтверждённым исходом и ссылкой на проект. Если шлюз сохранил только промежуточный результат, он показан отдельно. Исходную сводку и коды причин можно открыть в разделе «Запись шлюза».

В деталях задачи раздел «Исход задачи по данным шлюза» отдельно показывает выполнение, достижение цели, материалы и ревью. Время завершения привязано к подтверждённой попытке. Сохранённый результат, выделенный ответ и примечание шлюза показаны раздельно.

В «Публикации итогов» видны запись в комнате задачи и отдельная квитанция о сводке в Main. Пока шлюз ожидает публикации, окно перечитывает сведения о задаче.

В журнале задачи раздел «Сведения о доставке» показывает подтверждённые шлюзом состояния доставки, причины и путь к сохранённой копии. Счётчик повторов относится к записям журнала доставки.

Раздел «Работа, сохранённая при остановке» показывает, что осталось от дочерних задач и делегированных запусков. Полный отчёт можно открыть или скачать по квитанции шлюза.

Отчёт «Работа, сохранённая при остановке» открывается нативным просмотром Markdown из карточки задачи. Его можно перечитать или скачать целиком. Документ формируется шлюзом заново при чтении; при ошибке просмотра прежний текст остаётся с предупреждением. Новая квитанция остановки закрывает прежний просмотр и делает старые кнопки недействительными. Закрытие карточки отменяет чтение. Проверка: `npm run test:task-wrap-up:gjs`.

Когда шлюз предлагает продолжение задачи, запрос можно отправить из чата или деталей задачи. Повтор использует тот же идентификатор даже после перезапуска клиента. Подтверждённые попытки показаны вместе, прежние записи можно развернуть. Из Main видна текущая попытка задачи, перенесённой в проект.

В деталях задачи «События выполнения» читают журнал порциями или следят за ним до итогового снимка. Можно выбрать источник и открыть запись целиком в JSON. При остановке позиция сохраняется в открытом окне. Пропуски и смена области чтения показаны отдельно. Если шлюз больше не принимает курсор, журнал можно перечитать с доступного начала, сохранив на экране ранее полученные записи.

В форме «Новая задача» доступны рабочая папка на шлюзе, память, календарный срок, лимит выполнения, усилие, исполнитель, политики и критерии приёмки. Вложения можно загрузить с устройства или указать путём на шлюзе. Квитанция показывает подготовленные и отклонённые файлы. Если ответ на запуск потерян, та же форма восстанавливает запрос после перезапуска и проверяет сохранённую квитанцию по ID задачи.

В «Задачах» можно выбрать объём выдачи, задать состояния через запятую или открыть только снимок очереди. Поиск и фильтр текущего проекта работают по загруженной выдаче. «Открыть по ID» читает задачу напрямую, даже если её нет в списке. Если сохранённое состояние расходится со снимком очереди, видны оба факта.

В деталях задачи можно посмотреть сохранённый контракт, настройки исполнителя и проверку рабочей папки перед запуском. Текущие артефакты и предыдущие снимки показаны отдельно. Текстовые артефакты с опубликованными размером и SHA‑256 доступны для просмотра. Клиент сверяет эти значения при просмотре и скачивании. В манифесте результата можно увидеть основание сравнения и изменения файлов.

В деталях задачи и в её ревью показано, какие изменения ядра шлюз применил после перезапуска. Для каждого коммита журнал ревью показывает связь с проверенным деревом файлов и сохранённое решение автора. Если шлюз вернул неполный диапазон, клиент указывает это в списке коммитов.

«Переводы интерфейса» в настройках шлюза позволяют выбрать язык установки, просмотреть словарь и очередь генерации, импортировать или экспортировать JSON, отправить отсутствующие строки и пересоздать сгенерированный слой. Этот раздел управляет словарями Ouroboros. Интерфейс окна GNOME пока доступен на русском.

Из истории чата и комнат мест можно открыть изображения, воспроизвести аудио и видео, просмотреть текстовые файлы и скачать вложения. Кнопки ссылок открывают HTTP(S) в системном браузере. Вложения без сохранённого файла доступны из живого события, пока их данные есть в текущем чате.

PDF до 32 МиБ можно листать и увеличивать в окне GNOME из раздела «Файлы», чата, истории комнаты и материалов задачи. Для материалов задач клиент сверяет опубликованный размер и SHA‑256. Защищённый PDF запрашивает пароль в нативном поле; после открытия страницы доступны без повторного скачивания. Flatpak включает Poppler и его GLib bindings. При запуске из исходников нужны команды `pdfinfo` и `pdftoppm` из `PATH`, а для PDF с паролем — typelib `Poppler-0.18` для GJS.

После ошибки можно перечитать PDF или повторить подготовку страницы без повторного скачивания. Закрытие освобождает растр и завершает процесс Poppler; подготовка ограничена 12 секундами. Пароль передаётся дочернему процессу через stdin; перечитывание и закрытие сбрасывают его. Проверки: `npm run test:task-pdf:gjs`, `npm run test:pdf-password:gjs`.

Элементы просмотра PDF используют язык интерфейса шлюза и обновляются при изменении переводов без сброса страницы, масштаба или поля пароля. Имена файлов и пароли не передаются в очередь недостающих переводов. Проверка: `npm run test:pdf-i18n:gjs`.

Чат и файловый браузер загружают файлы блоками из временной копии. При отмене загрузки чат сохраняет текст и подтверждённые вложения. Если файл передан, а ответ шлюза потерян, клиент показывает неопределённый результат загрузки.

Перед добавлением загрузки в черновик чата клиент сверяет размер из квитанции, опубликованный SHA‑256 и ссылку на файл. Сверка относится к отправленной временной копии.

При удалении вложения из черновика чат показывает квитанцию шлюза. Если итог неизвестен, можно повторить удаление той же загрузки. Квитанции остаются в исходной комнате в течение текущего сеанса клиента.

## Разработка

Точка входа GTK находится в `src/main-gjs.ts`, экраны и транспорт libsoup — в `src/gjs/`. Сборка компилирует модули для Node и GJS по отдельности.

Для локального расчёта Mermaid, виджетов навыков с JavaScript или HTML и HTML-приложений в карточках чата нужен WebKitGTK 6.0. Он входит в рантайм Flatpak. Каждый такой виджет или приложение получает отдельный сеанс WebKit, а экран клиента и декларативные виджеты отображает GTK.

`npm run test:widget-runtime:gjs` проверяет исполнение виджетов через настоящий WidgetView: ESM с циклическими и динамическими импортами, классический JavaScript и HTML-вкладку навыка. Проверены применённый CSS, декодирование изображения, потоковые данные, ограниченные вызовы API, события, тема, ошибки и закрытие с отзывом аренды ресурсов. Сценарий прошёл на хосте и в GNOME 51 Flatpak; HTML-приложения карточек проверяются отдельно.

`npm run test:card-app:gjs` выполняет HTML-приложение через настоящий Cards/CardApp: сохранение состояния и повторное открытие, тема, размер, ошибки и результат в черновик без отправки сообщения. Проверены отказ от повреждённого HTML, неверного MIME-типа и недоступного приложения, изоляция и закрытие. Сценарий прошёл на хосте и в GNOME 51 Flatpak.

`npm run test:widget-session:gjs` проверяет декларативный виджет через реальные маршруты расширения: GTK-форму и действие, ожидание задания, опрос, SSE и WebSocket. Статус задания должен быть строкой; явный некорректный `status` не заменяется `state`. Шкалы прогресса не откатываются внутри одного задания. Скрытие приостанавливает опрос и поток, закрытие освобождает чтения и формы. Проверка прошла на хосте и в GNOME 51 Flatpak.

`npm run test:widget-board:gjs` проверяет настройки нативной доски: ширину, порядок и режимы запуска через настоящие меню GTK и API. Ручной режим ждёт нажатия, автоматический останавливает кадр при уходе с доски, «Оставлять работающим» сохраняет его. Явная остановка сохраняется при повторном открытии доски. Неполные ответы сохраняют последнюю подтверждённую версию; неизвестная запись не повторяется автоматически. Проверка прошла на хосте и в GNOME 51 Flatpak.

`npm run test:frame-recovery:gjs` запускает несколько отдельных процессов клиента и проверяет восстановление после прерванного старта виджета. До явного запуска виджет остаётся остановленным; сведения о прерывании отправляются через `/api/ui/holds`. Неполный или потерянный ответ сохраняет запись для повторной доставки, подтверждённые пачки отправляются целиком. Проверка прошла на хосте и в GNOME 51 Flatpak.

`npm run test:card-app-recovery:gjs` проверяет восстановление HTML-карточки тремя отдельными процессами: прерванный старт, ручное открытие с чистым состоянием и сохранённую явную остановку. Сообщение о прерывании попадает в комнату публикации карточки. Обычное повторное открытие в том же сеансе сохраняет состояние приложения. Проверка прошла на хосте и в GNOME 51 Flatpak.

`npm run test:contribution-actions:gjs` проверяет действия навыков через настоящий чат: вставку шаблона, уведомление, открытие доски и запрос с текстом черновика или ссылкой на ответ. Изменённый черновик и другая комната защищены от очистки. Согласно контракту, успешный HTTP 2xx допускает отсутствие JSON-уведомления; потерянный ответ не повторяется автоматически. Неполный каталог сохраняет прежние элементы, старые кнопки не выполняют отозванные действия. Проверка прошла на хосте и в GNOME 51 Flatpak.

`npm run test:contribution-preferences:gjs` проверяет скрытие и порядок элементов, выбор движков диктовки и озвучивания через GTK-формы. Ответ должен подтверждать выбранные значения; неполный или потерянный ответ сохраняет прежние подтверждённые настройки без автоматического повтора. Закрытие формы отменяет ожидание ответа, а старые переключатели не пишут настройки. Проверка прошла на хосте и в GNOME 51 Flatpak.

`npm run test:speech-runtime:gjs` проверяет запись тестового тона в WAV, передачу навыку и вставку ответа в настоящий чат, а также исполнение настоящего `device_voice`, локальный синтез eSpeak NG и декодирование через GStreamer. Проверяются новая hash-bound ревизия с изменёнными словами, очередь, pause/resume, события, отмена и недопустимые параметры. При изменении черновика или комнаты результат диктовки предлагается отдельно. Закрытие останавливает запрос и воспроизведение; старые кнопки не запускают работу. Тест использует бесшумный выход, без физического микрофона и моделей. На хосте без eSpeak применяется бинарник подготовленного Flatpak build: `OUROBOROS_SPEECH_BUILD=/path/to/build` либо путь из `/tmp/ouroboros-flatpak-proof-current`. В Flatpak используется его `/app/bin/espeak-ng`.

`npm run test:speech-codecs:gjs` проверяет все пять форматов диктовки: WebM, Ogg, MP4, MP3 и WAV. Записи проходят через реальные GTK-кнопки и HTTP-маршрут навыка; декодирование отдельно проверяется `wave`, `ffprobe` и `ffmpeg`. Эти два исполняемых файла нужны на хосте тестового сервера. Проверка прошла на хосте и в GNOME 51 Flatpak; микрофон, динамики и модели не используются.

`npm run test:host-module:gjs` проверяет базовый исполнитель клиентских модулей навыков: загрузку файлов указанной ревизии, `mount(ctx)`, регистрацию TTS/STT, вызовы и отмену. Отдельный процесс WebKit останавливается при закрытии или зависшем запуске. HostModules связывает каталог со страницей чата: нативный выбор клиентского STT/TTS, вставка расшифровки, отмена, смена комнаты, выбранный голос и удаление модуля проверяются через настоящий ChatPage. Приостановленный модуль запускается отдельной нативной кнопкой. Исполняются также неголосовые host entries; смена настоящей проверенной ревизии заменяет процессы. Panic через нативную кнопку, команду чата или общий запрос останавливает модули всех страниц подключения до ответа сервера и запрещает их повторный запуск при refresh. HTTP Fetch/XHR и `/static/...` imports используют нативную авторизацию; проверяются бинарные тела, потоковые ответы, отмена и Fetch redirects. Ответы передаются через ограниченную очередь native GIO. WebSocket использует настоящий WebKit с нативно установленной HttpOnly cookie: проверены авторизация, бинарные кадры >5 MiB, порядок, subprotocol, закрытие и удаление cookies при logout/Panic/close. Открытые нативные диалоги STT/TTS обновляют загрузку и доступность движков, сохраняют несохранённый выбор голоса и блокируют старые кнопки. Отдельный `test:host-module-recovery:gjs` проверяет аварийное завершение GJS после реального mount, остановленный запуск без чтения assets в следующем процессе, системную запись в истории владельца, ручной запуск и обычное повторное открытие. Этот сценарий прошёл на хосте и в GNOME 51 Flatpak. Стандартный `device_voice` теперь исполняется через общий модульный путь с нативным адаптером синтеза. Для доверенных host-модулей доступны настоящий WebKit `getUserMedia`, нативное разрешение на микрофон/камеру, индикатор и остановка захвата. `test:host-media:gjs` проверяет WebKit mock-устройства, MediaRecorder, точную загрузку байтов, отказ, закрытие и Panic. Микрофон и камера/экран имеют общий учёт владельцев для модулей, диктовки и звонков в процессе приложения. Конкурирующий запуск получает причину отказа до открытия устройств; клиентская диктовка передаёт право своему модулю. `test:capture-lease:gjs` проверяет конкуренцию, ожидание разрешения, mute/flush, отмену, поздний ответ портала и Panic. Распознавание речи и остальные возможности Web Speech ещё требуют завершения.

```sh
npm run build       # обе tsc
npm run typecheck   # проверка без эмита
gjs -m dist-gjs/main-gjs.js
node dist/cli.js check   # дым без GUI: health + state + история
```

Проверка авторизации использует настоящий `NetworkAuthGate` из закреплённого Ouroboros 7.10.0, временный сервер и каталог состояния. Для неё нужны исходники шлюза и Python с его зависимостями `starlette`/`uvicorn`:

```sh
OUROBOROS_REFERENCE=/path/to/ouroboros \
OUROBOROS_TEST_PYTHON=/path/to/venv/bin/python \
npm run test:auth:gjs
```

Дополнительная переменная `OUROBOROS_FLATPAK_BUILD=/path/to/build-dir` запускает этот же клиентский тест в уже собранном Flatpak. Проверяются HTTP/WebSocket с cookie и Bearer, вход/выход, смена пароля, межсайтовый запрет и разделение сеансов подключений.

С теми же переменными `npm run test:core:gjs` проверяет нативные формы проектов, файлов и расписаний через настоящий маршрутизатор шлюза. Python для этого прогона также требует `croniter`. Стенд создаёт отдельный каталог в `~/.cache`: выбор серверной папки по контракту ограничен домашним деревом. В журнале указан результат проверки 18 пар метод/маршрут; проверяются сохранённые данные, конфликты, Unicode/бинарные файлы, cron/однократное время и сохранность подключённой папки при удалении проекта. Системный выбор файла и подтверждение удаления получают тестовые ответы. На хосте сохраняются снимки GTK.

`npm run test:owner:gjs` использует те же переменные для нативных форм общих настроек и управления владельца с отдельной конфигурацией шлюза. Проверяются сохранение/конфликт/перечитывание обычного параметра, предупреждение о недоступных подключениях с позициями резервных маршрутов и его исчезновение после исправления, восемь маршрутов владельца, разделение Main и проекта, контекст, субагенты, усилие, безопасность и отметка о перезапуске. Тесты настроек и основных операций проверяют также буквальный вывод `<`, `>` и `&` в значениях и именах.

`npm run test:launch:gjs` проверяет нативную форму запуска через настоящий приём задач, хранилище результатов и сохраняемую очередь шлюза. Проверяются загрузка и байты вложения, частичный приём и отказ при неполном наборе, сохранение неизвестного исхода, точный повтор после проверки отсутствия задачи и восстановление квитанции без дубликата. Также проверяются рабочая папка, память, лимиты, политики, формат ответа и сохранение пробелов в тексте. Стенд использует отдельные данные и не исполняет задачи моделями; Python требует также `python-multipart`.

`npm run test:events:gjs` проверяет нативный журнал выполнения через настоящий SSE v2 шлюза: продолжение с физической позиции, запись с ранней датой, появление подзадачи, ротацию файла, фильтр источников и буквальный текст. Проверяются остановка слежения, ошибка непригодной позиции с явным перечитыванием и итоговый снимок. Используются те же переменные окружения и отдельное тестовое хранилище без запуска моделей. Старый GET-протокол проверяется после отказа POST с 405: числовая позиция, продолжение, остановка и итоговый снимок. При вставках с ранней датой этот протокол допускает повторы/пропуски; нативная форма предупреждает об этом и позволяет перечитать с нуля, сохранив прежние строки с пометкой. Ошибка доступа 403 не вызывает переход на GET.

`npm run test:controls:gjs` проверяет команды задач через настоящие обработчики и очередь: повтор паузы/ускорения после потери ответа с тем же ID, одну выдачу сообщения ускорения из почтового ящика, возобновление и остановку. Нативное окно берёт разрешённые действия из `/api/state`; тест нажимает паузу, возобновление и остановку, включая отказ в окне подтверждения. Задачи приняты настоящим API, но инертный рабочий слот их не исполняет. Проверка мягкой остановки подтверждает приём запроса, а не получение частичного результата от модели.

Сводка активной работы показывает `works_gaps`: причины неполноты, связанные задачи и предупреждение об устаревших сведениях. Компактная панель остаётся доступной при пустом неподтверждённом списке. Диагностика не подменяет серверные разрешения действий. Проверка: `npm run test:work-gaps:gjs`.

Снимок активной работы проверяется до применения: повреждённые или повторяющиеся записи сохраняют прежний список неподтверждённым и отключают команды до успешного чтения. Действие требует явного `confirmed`; отсутствие сведений о комнате не считается отсутствием работы. Старые кнопки повторно проверяют текущий снимок. Проверка: `npm run test:work-read:gjs`.

На экране активности сведения `/api/health.inline_executors` показаны нативно: текущие исполнители внутри процесса шлюза, объявленные резервные запуски этого процесса и недавние записи с причиной. Можно открыть задачу по точному ID. Недавняя запись не объявляется завершением задачи; ошибка диагностики сохраняет последние сведения неподтверждёнными и не скрывает остальную информацию о здоровье шлюза. Проверка: `npm run test:inline-executors:gjs`.

Панель запуска показывает готовность приёма сообщений и задач, именованные этапы с ошибками и временем, опубликованные фоновые задания с отдельными done/total и измерение задержки событий супервизора. Сбой необязательного этапа виден даже при общей фазе Ready. Пустой список опубликованных заданий не объявляется отсутствием заданий. Проверка: `npm run test:boot-status:gjs`.

Уже принятая задача может ждать проверки исходного доступа к проекту или области работы. Клиент показывает `project_admission_hold` в списке задач, очереди активности и окне задачи, включая пояснение шлюза и код причины. Окно задачи повторяет чтение, пока ожидание не снято; это не повторный запуск работы. Проверка: `npm run test:project-hold:gjs`.

Окно задачи отдельно показывает состояние Hurry: запрос записан, команда применена или задача завершилась до её применения. Доступны эффекты и история прежних попыток; ожидающее применение перечитывается автоматически. Проверка через настоящие API и обработчики typed mailbox: `npm run test:task-hurry:gjs`.

Окно задачи показывает хранение истории отдельно от результата выполнения: перенос в фоне, завершение и проблемы с причинами и счётчиками. Ожидающий перенос перечитывается автоматически; ошибка видна в заголовке свёрнутого блока. Проверка с настоящим API: `npm run test:task-history-retention:gjs`.

Если Resume возвращает вызовы с неизвестным исходом, нативная форма позволяет выбрать конкретные вызовы и ввести свою причину. Их повтор не разрешается. При выборе части списка задача может остаться на паузе, хотя решение уже записано; клиент предлагает перечитать задачу перед следующим решением. Выбор и причина сохраняются при смене языка. Проверка: `npm run test:task-resume-unknown:gjs`.

В окне задачи действие «Пауза с причиной…» позволяет указать необязательную причину владельца. Обычная «Пауза» остаётся доступна одним нажатием. Если ответ потерян, повтор сохраняет исходные ID и тело запроса; прежняя причина показывается без редактирования. Проверка: `npm run test:task-pause-reason:gjs`.

Неподтверждённые Pause, Hurry и Stop сохраняются до отправки в локальном журнале с правами 0600. После перезапуска они доступны в окне задачи для явного повтора с тем же запросом. Повтор проверяет актуальность попытки; результат Stop завершённой задачи можно сверить отдельно. Автоматической отправки при запуске нет. Проверка двумя отдельными процессами GJS: `npm run test:work-journal:gjs`.

Окно задачи различает выполняющуюся остановку и завершение с частичным результатом перед остановкой, показывает сохранённую шлюзом причину. Пока intent открыт, окно перечитывает сведения и не объявляет задачу остановленной раньше подтверждения. Ошибка чтения сохраняет последние сведения; закрытие снимает опрос. В списке задач также виден текущий режим остановки. Проверка: `npm run test:task-cancellation:gjs`.

Повреждённая или относящаяся к другой задаче квитанция сохраняет запрос для точного повтора. Клиент проверяет каждый ответ latch-повтора Pause и не принимает чужие task detail за результат Stop. Допустимые короткие ответы и дополнительные поля API поддерживаются; ссылка на преемника используется только для Continue. Проверка: `npm run test:work-receipt:gjs`.

`npm run test:continuation:gjs` проверяет настоящее создание продолжения прерванной задачи: сохранение nonce при пересоздании клиента, потерю ответа до/после приёма и восстановление после отказа записи очереди. Проверяются единственный преемник, исходные слова владельца, нативная навигация и отказы после остановки владельцем или истечения срока. Этот же прогон нажимает защиту материалов и её снятие в GTK, проверяет атрибуцию запроса шлюзом, отмену подтверждения и сохранность материалов после снятия защиты. Используются те же переменные и отдельное хранилище; модели не запускаются.

`npm run test:reviews:gjs` проверяет нативную историю по записям, созданным настоящим построителем review ledger шлюза. Проверяются замечания с обоснованием/свидетельством/рекомендацией, кворум, запрошенная и фактически указанная модель, состав проверки, результаты по разделам и число скрытых замечаний. Проверены страницы архива с отсутствующей соседней записью, полный длинный ответ и скачивание, отказ после изменения исходника и замаскированная выгрузка с отдельными SHA‑256 исходника и выданных байтов. Дополнительно проверены полный ответ участника плана, отказ при смене сохранённого исходника, обновление ссылки и проверки навыка из старого журнала и нового ledger с привязкой к задаче. Используются те же переменные и отдельное хранилище без запуска моделей.

В сведениях об участниках ревью видны наблюдаемая модель, зарегистрированные API/CLI-исполнители, HTTP-статус, код и причина отказа, время сброса лимита и раскрываемые подробности. Для плана назначенная модель подписана отдельно от наблюдения исполнения. Диагностика маскирует известные форматы ключей и поля учётных данных; тексты ревью и скачиваемые источники этот клиентский фильтр не меняет. Раскрытие вложенных участников плана сохраняется при обновлении.

Список возражений к плану различает подтверждённое отсутствие и неполное чтение. Повреждённые строки не превращаются в «возражений нет»; читаемые замечания сохраняются. Открытые возражения, история отзывов и недоступная прежняя проверка показаны раздельно. Проверка: `npm run test:plan-objections:gjs`.

`npm run test:places:gjs` проверяет нативное подключение места, параметры/события пробуждения, конфликт ревизий, чтение после потерянного ответа, дословные заметки и подтверждение/отзыв аккаунта владельца через настоящий API. Входящее событие сохраняется настоящим Presence capture без запуска фокуса; нативное окно открывает комнату и историю. После отключения проверяются помеченный кеш индекса и сохранность истории. Декларация коннектора проходит настоящий разбор манифеста и проекцию; его статус задаёт тестовый обработчик, внешние сервисы не вызываются.

`npm run test:places-read:gjs` проверяет целостность списка и квитанций Places. Повреждённая запись сохраняет прежний список и черновик. После неподтверждённой записи повтор блокируется до успешного перечитывания; конфликт ревизии сохраняет локальные изменения и отдельное поле другого клиента.

Закрытие окна «Мест», его родителя или настроек отменяет ожидание запросов. Старые элементы закрытого окна не отправляют действия. Если шлюз успел отключить место, новое чтение подтверждает отсутствие привязки и сохраняет ссылку на ранее прочитанную историю в текущем сеансе. Проверка: `npm run test:places-lifetime:gjs`.

Сведения об аккаунтах из статуса коннектора проверяются как целая декларация: неверный участник убирает производную кнопку подтверждения аккаунта. Варианты подключения сохраняют отдельные ID, даже если подписи совпадают; действие «Весь аккаунт» не выводит их из подписи. При известном пустом списке можно открыть объявленный раздел настроек коннектора, а при отсутствии такого раздела в декларации — навыки. Проверка: `npm run test:place-connector:gjs`.

`npm run test:cards:gjs` проверяет нативные карточки через настоящий card store и API: все 200 сохранённых действий, счётчик удалённых записей, повтор раннего недоставленного действия с прежними ID/значениями, закрепление и снятие закрепления, неизменность закреплённой версии и отказ устаревшего действия после замены карточки. Также читаются исходные байты HTML-приложения и проверяется запрет его закрепления. Исполнение приложения в WebKit этим тестом не проверяется; модели не запускаются.

`npm run test:card-lifetime:gjs` проверяет окно карточки и список закреплений через настоящий card store, API и почтовый ящик задачи. Неполные/чужие ответы сохраняют последнее содержимое и блокируют действия; квитанции проверяют ID запроса/карточки и состояние доставки. После неизвестного результата явный повтор сохраняет прежний request_id и не дублирует ввод. Старые кнопки тела/доставки/закрепления не действуют; смена чтения и закрытие отменяют принятые GET/POST до освобождения ответа стендом. Проверено восстановление закрепления после потерянного ответа и сохранение списка при malformed-ответе. Сетевые сбои заданы стендом; модели/worker не запускаются.

`npm run test:translations:gjs` проверяет шесть настоящих маршрутов i18n через нативное окно: язык/профиль/правила множественного числа, страницы и фильтр словаря, импорт/экспорт с сохранением слоя владельца и скрытого импортированного варианта, очередь отсутствующих строк, отменённое/подтверждённое пересоздание, английский и сброс выбора. Уведомление о новой ревизии блокирует запись по старому снимку до его обновления. Используются те же переменные и отдельные настройки/словари; генератор и модели не запускаются.

В настройках переводов доступен редактор профиля текущего языка: название, описание для переводчика, направление письма, полный лексикон и собственные правила множественного числа. Он загружает лексикон через экспорт, сохраняет словарь переводов и оставляет черновик при конфликте. После потерянного ответа точное перечитывание подтверждает сохранение без повторного POST. Проверка: `npm run test:language-profile:gjs`.

`npm run test:translation-lifetime:gjs` проверяет сохранение последнего словаря при ошибках вложенных полей, отмену старого чтения при новой ревизии и закрытие окна во время выбора файла, подтверждения, GET и скачивания. Настоящий импорт с потерянным ответом не повторяется автоматически; чужая квитанция не принимается. Экспорт сохраняет owner/shadow и Unicode, отменённый поток оставляет прежний файл. Ответы chooser/подтверждения и сетевые сбои управляются стендом; API и хранилище настоящие, генератор не запускается.

Параметр `welcome` из `/api/ui/preferences` отображается в пустом Main средствами GTK: `default`, `custom` и `hidden`. Собственный текст выводится буквально; это элемент интерфейса, который не записывается в историю и не отправляется модели. Приветствие появляется после успешного чтения полной пустой истории и скрывается во время загрузки, при ошибке, неполной выдаче или появлении сообщения. Для пустого Main клиент читает последнюю страницу целиком: ответ только с новыми записями не подтверждает пустоту всей истории. `npm run test:welcome:gjs` проверяет это через настоящий API предпочтений/истории; ошибки и неполная выдача задаются стендом, входящее сообщение приходит по тестовому WebSocket.

Дочерние работы в чате собраны в группы GTK по задаче и вложены по `parent_task_id`. Меню «Подзадачи» сохраняет `nested_subagents_expanded` на шлюзе. Ручной выбор раскрытия отдельной группы сохраняется в текущем окне; переход к точной записи раскрывает её предков. `npm run test:nested:gjs` проверяет это через настоящую историю, lineage и preferences API, включая повторное создание клиента и видимый вывод строк при циклической связи.

`npm run test:reads:gjs` проверяет нативные `RoomReadView`/`RoomReads` через настоящий dialogue store и preferences API: частичное и полное прочтение длинной строки при прокрутке, диалог поверх текста, раскрытие скрытой строки без прокрутки, пакеты по 64 общих адреса, повтор после недоступного ответа уже выполненной записи, независимые курсоры Main/проекта и восстановление после пересоздания. Используются те же переменные окружения стендов; модели не запускаются.

Главное окно использует нативную боковую навигацию `Adw.ViewSwitcherSidebar` (Libadwaita ≥ 1.9, включена в используемую платформу Flatpak 51). Кнопка «Навигация» открывает/скрывает панель; на узком окне она накладывается на содержимое. Меню «Ширина панели» сохраняет `sidebar_width` через API; 0 восстанавливает стандартные 280 пикселей. После неподтверждённой записи форма предлагает перечитать состояние. Чат под выдвинутой панелью не отправляет отметки прочтения. `npm run test:navigation:gjs` проверяет компонент и запуск всей точки входа с настоящей историей и отдельными локальными настройками.

Проект открывается в отдельном нативном диалоге Libadwaita, сохраняя Main под ним. При закрытии или смене проекта остаются черновики каждой комнаты; два чата используют одну очередь неподтверждённых отправок. Меню панели сохраняет `project_panel_width` (320–1100 пикселей; 0 — стандартные 440). Кнопка обновления перечитывает проект и ширину. Переходы к сообщениям и задачам открывают соответствующий чат; Main под диалогом не подтверждает прочтение. `npm run test:project-panel:gjs` проверяет это через настоящий API, включая минимальную нативную ширину, конфликт переходов и восстановление после потери ответа. Сообщения в стенде не отправляются, модели не запускаются.

Ответы на вопросы и причины закрытия принимают многострочный текст до 2000 символов Unicode без удаления краевых пробелов. При превышении лимита текст остаётся в форме, отправка блокируется. Публикация вопроса и доставка ответа показываются раздельно; неподтверждённое действие повторяется с прежними данными и ID. `npm run test:questions:gjs` проверяет нативные формы в Main/проекте через настоящий API, сохранённые вопросы, почтовый ящик задачи и состояния по WebSocket. Проверяются поздний ответ и скрытие неизвестной доставки с подтверждением. Модели и получатель позднего сообщения в стенде не исполняются.

Формы обычных и секретных вопросов показывают причину, автора, время и идентификаторы закрытия. Обычная форма отдельно показывает поздний ответ и явное подтверждение шлюза о передаче в чат; общий статус доставки такого подтверждения не заменяет. `npm run test:question-lifecycle:gjs` проверяет настоящий поздний decision ingress и закрытие владельцем/моделью, перечитывание, устаревшую квитанцию, неполные метаданные и живые переводы на хосте и в Flatpak. Выполнение модели в стенде не запускается.

Материалы вопроса открываются отдельной кнопкой: доступны текст, изображения, PDF, аудио/видео и скачивание файлов с проверкой размера и SHA‑256. Подпись сохраняется отдельно от имени сохранённого артефакта. Закрытие вопроса отменяет вложенные просмотры и выбор места сохранения; черновик ответа не теряется при обновлении материалов. Проверка: `npm run test:question-materials:gjs`.

Личные обращения из связанных мест показывают сохранённый шлюзом источник отдельно от слов сообщения: имя места, исходную задачу в подсказке и HTTP(S)-ссылку. Подпись доступна также в окне вопроса, обновляется вместе с языком и сохраняет черновик ответа. Проверка: `npm run test:contact-source:gjs`.

Чат учитывает имя отправителя из API: внешние сообщения показывают `sender_label`, Telegram без имени имеет отдельную подпись, а сообщения владельца из другого окна остаются «Вы». Отдельно обозначены Consciousness, сводки задач, ревью навыков и ход работы. Живые медиа сохраняют автора и источник обращения. Проверка: `npm run test:chat-sender:gjs`.

Переданные другой работе сообщения владельца (`relay`) показаны отдельным нативным блоком: все исходные цитаты, имена вложений, место и время, сводка и получающая работа. Каждую цитату можно раскрыть и открыть в исходной истории; раскрытие сохраняется при обновлении и смене языка. Проверка: `npm run test:chat-relay:gjs`.

Обычная цитата ответа показывает автора, время и полную длину исходного текста, если шлюз сократил preview. `unresolved` означает недоступность при сохранении ответа и оставляет возможность нового поиска. Переходы поддерживают строки и карточки работ (`task:`); некорректные сведения не создают кнопок навигации. Проверка: `npm run test:chat-reply-quote:gjs`.

Нативная форма запроса секрета показывает, какие ключи читают установленные навыки и какие разрешения уже выданы. Сохранение не выдаёт новых разрешений. Смена состояния ключа другим клиентом требует перечитывания и явной замены; после потери ответа значения не пересылаются автоматически. Подтверждение отмены принадлежит форме и закрывается при её отзыве. `npm run test:secret-questions:gjs` проверяет настоящий защищённый API и Settings writer на синтетических значениях, включая позднее сохранение без запуска работы и честное отображение неизвестного результата прерванной записи. Навыки и модели в стенде не исполняются.

## Релизы

Версия живёт в `package.json` + `CHANGELOG.md`. Релиз: обнови оба, коммит, тег `vX.Y.Z`, пуш тега — бандл соберётся сам (см. `.github/workflows/flatpak.yml`).

`npm run test:native-i18n:gjs` проверяет применение словаря к явно отмеченным нативным подписям: разделам навигации, подсказкам верхней панели, настройкам ширины и основным кнопкам/подсказке ввода чата. Язык и импорт словаря обновляются через настоящий API и WebSocket; проверены plural map, направление отдельных виджетов, сохранение последнего подтверждённого словаря при ошибке и отбрасывание старого чтения. Пользовательский текст, имена и код не переводятся и не попадают в очередь отсутствующих строк; параметры передаются в неё только своими именами. Это частичная миграция подписей GTK: часть настроек теперь покрывает отдельный сценарий ниже; остальные формы и раскладка всего окна для RTL пока не переведены на этот механизм.

`npm run test:settings-i18n:gjs` проверяет живые переводы основных кнопок, заголовков и поиска настроек, окон нового секрета и динамического счётчика изменений через настоящий API словаря и WebSocket. Проверяются RTL/возврат к английскому, обновление словаря без переоткрытия и неизменность технических ключей, значений, подписей из метаданных и введённого пароля; эти данные не попадают в missing reports. Сохранение параметров и секретов сценарий не выполняет.

`npm run test:i18n-integrity:gjs` проверяет общую строгую проверку ответа словаря в редакторе и живых подписях: повреждённый элемент, plural/profile/stats/languages/generator и memory_error не заменяют подтверждённые текст/направление/ревизию. Завышенная ревизия повреждённого ответа не блокирует последующее восстановление по настоящему API.

`npm run test:settings-labels-i18n:gjs` проверяет живой перевод встроенных названий параметров и заголовков редакторов, поиск по переведённой подписи и техническому ключу, сохранение числового черновика и неизменность подписей/значений из метаданных. Проверка проходит через настоящий API словаря и WebSocket, без записи параметров шлюза.

`npm run test:review-policy-i18n:gjs` проверяет живые переводы политики ревью, варианты режимов, пояснения и ошибки, сохранность выбранных machine IDs и лимита, unknown/unlimited значения, закрытые callbacks. Patch из формы передаётся настоящему обработчику настроек и подтверждается чтением; запуск ревью и модель не выполняются.

`npm run test:dialog-i18n:gjs` проверяет живые переводы Cancel/Close и явно заданных статических heading/body/action подтверждений настроек через настоящий API/WebSocket. Default/close response остаётся cancel; Cancellable и поздний OK не дают подтверждения после отмены. Пользовательские заголовки/тексты/действия без source keys не переводятся и не отправляются в missing reports.

`npm run test:owner-i18n:gjs` проверяет живые переводы полей и режимов владельца, сохранение выбранного ID и текстового черновика при смене языка, точную запись owner API, отмену принятых GET/POST при закрытии и корректное повторное открытие. Имена проектов, модель и правила остаются данными и не входят в missing reports; модель и команды жизненного цикла хоста не запускаются.

`npm run test:saved-secrets:gjs` проверяет чтение выбранного сохранённого секрета через настоящую ручку `/api/settings/secret`: из общих настроек, встроенного/дополнительного подключения провайдера и формы MCP. Значение находится в нативном поле пароля только для чтения с кнопкой показа; закрытие формы очищает поле и отменяет запрос. Проверяются пользовательский ключ, токен и регистронезависимый заголовок MCP, пустое значение, отсутствующие/неоднозначные записи, HTTP-ошибка и задержанный ответ. Пассивное чтение остаётся маскированным, настройки не изменяются, провайдеры и MCP-серверы не вызываются. Стенд использует только синтетические значения в отдельном Settings и те же переменные запуска, что другие API-прогоны.

`npm run test:schedule-holds:gjs` проверяет удержания отложенной работы через настоящий API расписаний и нативные формы: отличие наблюдаемого ограничения от записанного удержания, обязательные причина и выбор связи, снятие конкретного hold_id, сохранение исходного бюджета/срока для связанной работы и отдельная связь для самостоятельной. Проверяются новый Stop до отправки и после проверочного GET, восстановление по свежему удержанию и потеря ответа после успешной записи без автоматического повтора. Используются отдельные настройки/хранилище и те же переменные запуска; задачи и модели не запускаются.

`npm run test:schedule-once:gjs` создаёт однократное расписание в нативной форме и запускает настоящий проход планировщика с неисполняющими worker-слотами. Проверяются одна запись в очереди, сохранённая квитанция accepted/dispatch=none, consumed-состояние и отсутствие дублей при повторных проходах. Кнопка последней задачи открывает настоящую нативную форму TasksPage и читает запланированную задачу. Форма блокирует повторное включение на тот же момент времени, включая эквивалентное UTC-смещение; новое время явно перевооружает расписание, сохраняя связь с прежним запуском. Код задачи и обращения к модели не исполняются.

`npm run test:schedule-lifetime:gjs` проверяет сохранение списка при неполных/дублирующихся записях и блокировку записи при непригодном preflight. Редактор, lifecycle-форма и проверка результата отменяют свои запросы при закрытии; скрытая страница отменяет чтение, закрытая прекращает polling. Принятые POST действительно меняют отдельное хранилище, после закрытия состояние восстанавливается чтением без повтора. Неизвестное значение усилия из ответа остаётся видимым и не сбрасывается молча; текущий шлюз отклоняет его, после явного выбора допустимого значения форма сохраняется. Сетевые/структурные ошибки управляются стендом; планировщик и worker/model не запускаются.

В дополнительных параметрах расписания доступны многострочные контекст, ожидаемый результат и ограничения, отдельный срок задания с UTC-смещением, разрешённые ресурсы и контракт в виде JSON-объектов, вложения в виде массива объектов. Они сохраняются в шаблоне и передаются новым запускам. Очистка поля удаляет его из шаблона; уже принятая задача сохраняет прежние параметры. Вложения здесь описывают файлы шлюза, загрузка локального файла этой формой не выполняется. Расширенный `test:schedule-once:gjs` проверяет эти поля до и после настоящего допуска в очередь, сохранность при переносе времени, явную очистку и отказ неверной структуры JSON/срока без UTC-смещения.

В форме запуска задачи ожидаемый результат и ограничения используют нативный многострочный ввод. Расширенный `test:launch:gjs` проверяет отступы, пустые строки, Unicode и конечный перевод строки при обычной записи и после неизвестного исхода: сохранение запроса на диск, повторное открытие формы и точный повтор после отсутствующей квитанции. «Оставить без повтора» очищает сохранённый запрос, сохраняет текст в открытой форме и освобождает новый идентификатор; повторное открытие больше не восстанавливает отменённый повтор.

Редактор файлов допускает буквальный символ `�` в корректном UTF-8 после побайтовой сверки полного текста с `/api/files/content`. Повреждённая кодировка, недоступное чтение байтов и несовпадение с предпросмотром оставляют файл доступным только для просмотра/скачивания. `test:core:gjs` проверяет эти случаи через настоящие read/content/write, вместе с прежними операциями файлов, проектов и расписаний.

`test:core:gjs` также проверяет потерянные квитанции файловых операций. После 503 до записи редактор сохраняет черновик, перечитывает прежнюю версию и разрешает явное повторное сохранение. После 503 вслед за успешной записью перечитывание подтверждает текст без нового POST. При потерянном ответе копирования/перемещения кнопка вставки скрыта, а проверка обеих папок показывает только текущее наличие элементов, не подтверждая задним числом операцию и не повторяя её. Выбор другого файла не заменяет неразрешённый перенос; результат можно закрыть.

В окне «Модели… → Параметры ролей…» аккаунт, окно контекста и режим обработки редактируются нативными полями для Main, Light, Safety, Vision, фоновой работы, глубокого саморевью и веб-поиска. Для резервных моделей каждый параметр имеет свой упорядоченный список. Флажок отличает отсутствие параметра от явного Auto/0/наследования. Правки сначала попадают в форму моделей, затем в общие несохранённые настройки.

В каталоге субагентов поле аккаунта доступно для сессий и управляемых моделей `claudexor::`. Обычная правка сохраняет закреплённый профиль; пустое поле включает Auto. Профиль также виден в строке каталога. Выбор API-модели из каталога меняет модель, а привязку аккаунта владелец задаёт отдельно.

Выбор сессии сохраняет исходные инструмент, профиль и модель, даже если шлюз не перечислил их в текущем каталоге: такие значения помечаются как неподтверждённые. Смена аккаунта сохраняет выбранную модель. При ошибке обновления предыдущий снимок доступен только для просмотра; закрытие родителя отменяет чтение и закрывает выбор.

`npm run test:session-picker:gjs` проверяет выбор сессии через настоящий status fan-out шлюза и локальный HTTP daemon-стенд, включая модели разных аккаунтов, частичный каталог, повреждённые ответы и отмену принятого GET до освобождения ответа.

«Каталог субагентов → Предложенный состав…» передаёт шлюзу текущий несохранённый состав. Можно сохранить свои строки и отметки ревью, разрешить пустой пул или снять флажок сохранения строк для генерации нового состава. Изменение каталога после расчёта требует пересчитать предложение. Правки остаются в форме до обычного сохранения настроек.

«Каталог субагентов → Доступность маршрутов…» показывает для управляемых моделей `claudexor::` наличие модели в каталоге выбранного источника и аккаунта, проблемы профиля и сведения о снимке. Пустой и недоступный каталоги различаются; частичный Auto показывает состояния аккаунтов отдельно. При ошибке обновления предыдущие сведения помечаются как неподтверждённые. Это информация каталога на момент чтения; запуск проверяет шлюз.

`npm run test:subagent-availability:gjs` проверяет настоящий model-catalog mapper, точные области source/profile и объединение одинаковых запросов, состояния аккаунтов, несовпадающие/повреждённые ответы, независимые ошибки status/catalog и отмену при закрытии окна.

«Каталог субагентов → Выполнения субагентов…» показывает последние сохранённые записи API: запрошенные параметры, наблюдаемый маршрут попытки и отдельную резервную попытку с её моделью, аккаунтом, вызовом и временем. Исторические маршруты подписаны по самой записи, включая удалённые строки. Отсутствующая история отличается от пустой; ошибка обновления сохраняет последний прочитанный снимок.

В нативных настройках голосовых вызовов окно разговора, принятый объём входа и рабочий резерв показаны отдельно, вместе с источником, датой и возможностями модели. Принятый вход не подменяет неизвестное окно. Неоднозначное подтверждение сохранения требует перечитать фактические настройки перед повторной записью.

Если настройки вызовов не читаются, нативная форма предлагает «Восстановить выключенные вызовы…». После явного подтверждения шлюз сбрасывает предпочтения к своим стандартным значениям и выключает вызовы. Окно предупреждает о сбросе движка, голоса, инструкций и завершении активных вызовов; по умолчанию выбрана отмена. Потерянный ответ сначала проверяется чтением.

`npm run test:call-recovery:gjs` проверяет этот путь через настоящий обработчик навыка: повреждённый JSON, неверные типы, отказ от подтверждения, восстановление серверных defaults, неизвестный исход и отмену при закрытии окна. Аудиосессии не запускаются.

`npm run test:call-session:gjs` проверяет нативный контроллер звонка с подменёнными транспортом и аудио: принадлежность admission, завершение при ожидающем POST, таймер начального состояния, PCM sequence/epoch wrap, mute и привязку controls к текущему call_id. `npm run test:call-video:gjs` проверяет видеопуть через настоящий GStreamer с `videotestsrc`, JPEG-кодирование/декодирование, CallSession/Gateway/Soup и первичный WebSocket/LiveCallHub. Проверены смена источника/настройки камеры, одинаковые кадры и epoch, share controls, поздние разрешения, отсутствие первого кадра и освобождение ресурсов. `npm run test:call-portal:gjs` вызывает настоящий `openPortalVideo`, libportal и экспорт родительского GTK-окна через изолированную D-Bus-службу протокола ScreenCast/Camera.
